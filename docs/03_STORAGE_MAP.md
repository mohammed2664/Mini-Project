# RentSphere Storage Map

This is the quick reference for where RentSphere stores listings, wallet/escrow data, users, locker state, payments, and logs.

## Important idea

RentSphere does not use MySQL or another external database. The Java server loads the records from `data/` when it starts and writes changes back to human-readable pipe-delimited text files. The in-memory Java objects handle the live rental state while these files provide persistence between restarts.

## Production data files

| File | What it stores | Main Java owner |
|---|---|---|
| `data/assets_ledger.txt` | Master equipment catalog: asset ID, name, category, daily price, deposit, host, status, specifications and location | `persistence/FlatFilePersistenceEngine.java` |
| `data/locker_grid_8x8.txt` | 64 pickup bays, row/column, compartment size, occupied status, assigned asset, device state, OTP and simulated sensor values | `persistence/FlatFilePersistenceEngine.java`, `locker/SmartLockerGrid8x8.java` |
| `data/escrow_vault.txt` | User wallet balances and locked rental collateral | `persistence/FlatFilePersistenceEngine.java`, `escrow/EscrowVault.java` |
| `data/users_auth.txt` | User accounts, roles, PBKDF2 password hashes, account status and timestamps | `auth/AuthService.java` |
| `data/payments_ledger.txt` | Sandbox payment orders, booking IDs, rent, deposit, total, provider status and payment ID | `payment/SandboxPaymentAdapter.java` |
| `data/disputes_ledger.txt` | Damage disputes, evidence notes, collateral and arbitration result | `dispute/DisputeService.java` |
| `data/policy_acceptance.txt` | Versioned policy-consent records | `policy/PolicyService.java` |
| `data/support_tickets.txt` | Grievance and support tickets with status and timestamps | `support/SupportService.java` |
| `data/notifications_log.txt` | Persisted user notifications | `support/NotificationService.java` |
| `data/audit_wal.txt` | Append-only audit/write-ahead log for important rental and settlement actions | `persistence/FlatFilePersistenceEngine.java` |

## Where the listing cards come from

The marketplace listing cards are built from backend asset records loaded from `data/assets_ledger.txt`. The frontend renders them in `frontend/js/app.js`; the page structure is in `frontend/index.html` and the visual styling is in `frontend/css/styles.css`.

The browser does not maintain a separate permanent catalog. It requests the current catalog from the Java server API.

## Where the wallet and escrow information comes from

Wallet balances and locked deposits are stored in `data/escrow_vault.txt`. A reservation normally affects both the asset record and the escrow record. Payment order details are recorded separately in `data/payments_ledger.txt`. The audit trail for the operation is written to `data/audit_wal.txt`.

## Test data

Folders named `data/test_*` are isolated files created by automated tests. They are not the live application database and can be regenerated by the test suite. Do not confuse them with the production files directly under `data/`.

## What is simulated

- The payment adapter is a sandbox, not a real bank or Razorpay account.
- Locker doors and sensors are simulated by Java classes.
- The escrow vault is an academic wallet/ledger model, not a regulated banking escrow account.
- Flat files are suitable for this portable OOT lab prototype. A production deployment would replace them with a transactional database.

## Safe handover rules

1. Do not delete or empty the files directly under `data/` before making a backup.
2. Do not commit real passwords, API keys or private credentials.
3. Use the automated tests' isolated `data/test_*` folders for experiments.
4. If the live data is changed during a demo, restore the backup or re-seed the demo data before presenting.
5. To inspect recent actions, read the last lines of `data/audit_wal.txt`.
